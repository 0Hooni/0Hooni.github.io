# Write-Post 스킬

지금까지의 대화 내용을 바탕으로 토스 테크니컬 라이팅 3단계를 적용해 Jekyll 블로그 포스트를 작성한다. 포스트 작성은 로컬 빌드와 결과 화면 검토가 끝났을 때 완료된다.

## 프로젝트 컨텍스트

모든 경로는 저장소 루트 기준이다.

| 항목 | 경로 |
|------|------|
| 포스트 저장 | `_posts/` |
| 템플릿 | `template/New Post.md` |
| 이미지 | `assets/img/post/{연도}/` |

### Front Matter 형식

```yaml
---
title: "[카테고리약어] 제목"
date: YYYY-MM-DD HH:MM +0900
categories:
  - 상위 카테고리
  - 하위 카테고리
tags:
  - 태그1
  - 태그2
---
```

### 카테고리 구조

프로젝트의 기존 포스트와 `AGENTS.md`를 우선 확인한다. 기본 구조는 다음과 같다.

| 상위 카테고리 | 하위 카테고리 |
|---------------|---------------|
| Mobile | iOS, Android, ReactNative |
| Web | React, ... |
| Backend | NestJS, SpringBoot, ... |
| Game | Unity, ... |
| Language | Swift, Kotlin, TypeScript, Go, ... |
| DevOps | CI/CD, Docker, ... |
| CS | ComputerScience, Algorithm, DataStructure, DesignPattern |
| Log | Boostcamp, 회고, 후기 |

### 작성 컨벤션

- 파일명: `YYYY-MM-DD-제목.md`. 오늘 날짜를 기준으로 한다.
- 섹션 제목: `## 이모지 제목`
- 마지막에 `## 🔗 레퍼런스` 섹션을 포함한다.
- 강조 블록으로 `{: .prompt-info }`, `{: .prompt-tip }` 등을 사용할 수 있다.

### 누적 레퍼런스

글을 쓰기 전에 다음 파일을 모두 읽고 적용할 항목을 확인한다.

| 파일 | 내용 |
|------|------|
| [`references/chirpy-theme.md`](references/chirpy-theme.md) | Chirpy 테마의 Mermaid, 수식, 이미지, Prompt 박스, TOC 동작 |
| [`references/user-preferences.md`](references/user-preferences.md) | 서론 구성, 표와 단락의 기준, 톤에 관한 사용자 선호 |
| [`references/failure-cases.md`](references/failure-cases.md) | 반복하지 않아야 할 과거 실패 사례 |

사용자 피드백이나 렌더링 실패에서 새 규칙을 발견하면 해당 참조 파일에 즉시 누적한다. 실패 사례는 증상, 원인, 해결의 세 부분으로 기록한다.

## 실행 단계

### 1. 사전 확인

이전 대화에 문서화할 학습 또는 트러블슈팅 내용이 있는지 확인한다.

내용이 없다면 다음과 같이 안내하고 종료한다.

> 문서화할 대화 내용이 없습니다. 먼저 `teaching-mode` 또는 `troubleshoot` 스킬로 세션을 진행해주세요.

### 2. 문서 유형 정하기

대화에서 문서 목표, 독자 수준, 문서 유형을 파악하고 사용자에게 확인한다.

| 유형 | 설명 | 적합한 경우 |
|------|------|-------------|
| 학습 중심 | 단계별로 따라 하며 배우는 튜토리얼 | 새로운 기술이나 개념 소개 |
| 깊은 이해 | 원리와 배경을 설명하는 개념 문서 | 기술의 동작 방식이나 철학 설명 |
| 문제 해결 | 특정 문제의 해결 과정을 다루는 문서 | 트러블슈팅이나 사용 가이드 |
| 참조 | API와 설정을 정리한 레퍼런스 | 빠른 참조가 필요한 정보 |

유형별로 다음 요소를 포함한다.

- 학습 중심: 학습 목표, 사전 준비, 각 단계의 목적과 안내, 실행 가능한 코드 예제, FAQ
- 깊은 이해: 등장 배경과 문제, 기본 원리, 다른 접근 방식과 비교, 시각 자료, 실제 사용 사례
- 문제 해결: 문제 상황, 원인이나 배경지식, 해결 단계, 실행 가능한 코드와 명령어, 환경별 차이, 해결 원리
- 참조: 간결한 개요, 구문과 파라미터, 반환 값, 여러 예제, 관련 API, 주의사항과 제한사항

다음 형식으로 분석 결과를 제시한다.

```text
분석 결과:
- 문서 목표: {파악한 목표}
- 예상 독자: {파악한 수준}
- 추천 유형: {추천 유형}

맞으신가요? 다른 유형으로 변경하실 수 있습니다.
```

### 3. 정보 구조 만들기

결정된 문서 유형에 맞춰 구조를 설계한다.

1. 한 페이지에는 하나의 목표만 둔다. 제목 깊이가 H4 이상이면 문서 분리를 고려한다.
2. 기본 개념에서 상세 내용으로 이어지는 예측 가능한 구조를 만든다.
3. 독자가 얻을 가치를 먼저 보여준다.
4. 핵심 키워드가 포함된 30자 이내의 평서문 제목을 쓴다.

구조 초안을 작성한 뒤 사용자에게 확인한다.

### 4. 문장 다듬기와 포스트 작성

확인된 구조를 바탕으로 본문을 작성한다.

1. 한 문장에는 하나의 생각만 담고 필요한 정보만 쓴다.
2. 앞서 설명했듯이 같은 메타 담화를 최소화한다.
3. 모호한 표현 대신 직접적이고 구체적인 언어를 쓴다.
4. 같은 개념에는 같은 표현을 쓰고 약어는 처음 등장할 때 풀어 쓴다.
5. 수동형보다 능동형을 사용하고 독자가 행동의 주체가 되게 한다.

표, 단락, Mermaid의 선택 기준은 참조 문서를 따른다.

### 5. 포스트 파일 생성

Front Matter와 작성 컨벤션을 적용해 `_posts/YYYY-MM-DD-제목.md`를 만든다.

- 같은 날짜와 제목의 파일이 있으면 덮어쓰기 전에 사용자에게 확인한다.
- 기존 구조에 없는 카테고리가 필요하면 사용자에게 확인한다.
- 이미지가 필요하면 `assets/img/post/{연도}/`에 둔다.

### 6. 로컬 빌드와 링크 검증

저장소 루트에서 다음 명령을 실행한다.

```bash
mise exec -- bash tools/test.sh
```

이 명령으로 프로덕션 빌드와 내부 링크를 검증한다. 의존성이 누락되어 실행할 수 없으면 임의로 설치하지 말고 사용자 승인을 요청한다.

실패하면 오류를 고치고 명령이 통과할 때까지 반복한다.

### 7. 로컬 서버 실행과 실제 URL 확인

다음 명령으로 localhost 서버를 실행한다.

```bash
mise exec -- bash tools/run.sh
```

- 포트가 이미 사용 중이면 해당 프로세스가 같은 저장소의 Jekyll 서버인지 확인한다.
- 같은 저장소의 서버라면 재사용한다.
- 다른 프로세스라면 사용 가능한 localhost 포트를 선택해 Jekyll 서버를 실행한다.
- 생성된 HTML이나 서버 경로에서 대상 포스트의 실제 URL을 찾는다. permalink를 추측하지 않는다.
- 실제 URL에 HTTP 요청을 보내 성공 응답과 본문 수신을 확인한다.

### 8. 화면 렌더링 검토

사용 가능한 브라우저 자동화 기능으로 실제 URL을 연다. 다음 항목을 확인한다.

- 제목, 본문, 사이드바 TOC, 코드 블록
- 포스트에 포함된 경우 이미지, Mermaid, 수식, Prompt 박스
- 내용이 잘리거나 겹치지 않는지, 원문 코드가 그대로 노출되지 않는지

문제가 있으면 포스트를 수정하고 로컬 빌드, HTTP 확인, 화면 검토를 다시 수행한다.

브라우저 자동화 기능을 사용할 수 없다면 빌드와 HTTP 검증까지 수행한다. 최종 보고에 시각 검토를 수행하지 못한 이유를 명시하고 서버는 유지한다.

### 9. 최종 보고

다음 항목을 보고한다.

```text
포스트 작성 완료

- 파일: _posts/YYYY-MM-DD-제목.md
- 유형: {문서 유형}
- 카테고리: {상위} > {하위}
- 로컬 URL: {실제 URL}
- 검증: 프로덕션 빌드, 내부 링크, HTTP 응답, 화면 렌더링
- 서버: 실행 중. 중지를 요청할 때까지 유지
```

화면 검토에서 대상 요소가 포스트에 없었다면 포함되지 않아 검토 대상이 아니었다고 구분한다. 커밋은 사용자가 요청할 때만 만든다.

## 완료 기준

- 포스트 파일이 작성되었다.
- 프로덕션 빌드와 내부 링크 검사가 통과했다.
- 실제 포스트 URL의 HTTP 응답을 확인했다.
- 가능한 환경에서는 화면 렌더링을 검토하고 문제를 수정했다.
- 사용자가 확인할 수 있도록 localhost 서버를 유지하고 정확한 URL을 보고했다.
